# Phase 2C Architecture: Planner & Task State

## Overview
Phase 2C introduces the ability to break down complex intents (`complex_task`) into an ordered sequence of logical steps using a generative LLM. It also establishes the core SQLite-backed persistence foundation for the Task Lifecycle without executing actual tools.

## Architecture Components

### 1. Planning Provider (`PlanningProvider` / `OllamaProvider`)
- Abstraction: `PlanningProvider` allows any AI service to generate structured `TaskPlan` json.
- Concrete Implementation: `OllamaProvider` inherits from both `LLMProvider` (Phase 2B) and `PlanningProvider` (Phase 2C). It reuses the exact same `httpx` logic. No secondary HTTP client was added.

### 2. Planner (`core/eva_core/task/planner.py`)
- Takes an unstructured user request for a complex task and prompts the LLM to return an array of plan steps.
- **Validation**: 
  - Validates Step count (capped at `MAX_PLAN_STEPS` = 10).
  - App assigns UUIDs natively instead of relying on the LLM.
  - Generates linear dependencies automatically if the LLM omits dependencies.
  - Retains and validates explicit dependencies if provided (discarding out-of-bounds).
  - **Cycle Detection**: Validates the task DAG using Depth-First Search to reject circular step dependencies or self-referential steps.

### 3. Task State Manager (`core/eva_core/task/state.py`)
- Tracks the state transition of tasks via a defined `TaskStatus` enum.
- Interacts purely with the `tasks` and `task_steps` tables in the existing SQLite `eva.db`.
- Safely serializes dependencies, results, and errors to JSON text fields.
- Provides strict lifecycle gating (e.g. A `COMPLETED` task cannot be transitioned back to `RUNNING`).

## Database Schema Changes (SQLite)
Added two tables to the Phase 1 schema:
- `tasks`: Fields for `task_id`, `request_id`, `intent`, `status`, `current_step`, `total_steps`, `result`, and timestamps.
- `task_steps`: Fields for `step_id`, `task_id` (foreign key), `sequence`, `description`, `dependencies` (JSON array), `status`, and timestamps.

## Task Lifecycle (State Transitions)
The application strictly enforces valid state transitions:
| From State | Valid Next States |
| --- | --- |
| `CREATED` | `PLANNING`, `CANCELLED` |
| `PLANNING` | `PLANNED`, `REQUIRES_CLARIFICATION`, `FAILED`, `CANCELLED` |
| `PLANNED` | `READY`, `CANCELLED` |
| `READY` | `RUNNING`, `CANCELLED` |
| `RUNNING` | `COMPLETED`, `FAILED`, `CANCELLED` |

*Note: Phase 2C successfully transitions up to `PLANNED`/`REQUIRES_CLARIFICATION`. The `READY` and `RUNNING` states are reserved for Phase 2D (Executor).*

## UI Interpolation Fix
A string interpolation bug existed in the Flutter UI (`${msg['status']}`) where the Dart compiler read literal string definitions generated by Python string replacers. This was corrected, and the UI was expanded to recursively render `TaskModel` contents (Task ID, Status, and individual steps with their pending states) directly in the chat layout.
